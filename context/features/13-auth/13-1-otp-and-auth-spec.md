# PART 1 — Why we have an OTP at all

An OTP (One-Time Password) is a short code, valid briefly, sent to something you
already own — an inbox or a phone. It proves you control that address.

**In this project the OTP is a recovery tool, not a login method.**

| | Password login | OTP |
|---|---|---|
| Used for | Every normal sign-in | Forgotten password only |
| Cost per use | ₹0 | ₹0 by email, ₹0.15–0.25 by SMS |
| Works offline / bad signal | Yes | No |
| Speed | Instant | 5–60 seconds of waiting |

**The reasoning:** 423 accounts logging in on most school days, at ₹0.20 an SMS,
would be roughly ₹25,000 a year — for a worse experience than typing a password.
Apps that use OTP as the primary login (Swiggy, Uber) do it because they have no
password at all and a huge advertising budget. A school app has neither.

So: password first, OTP only when the password is lost.

# PART 2 — The OTP contract

Every property below is enforced in code. Changing any of them means changing
`lib/repos/authRepo.js` and re-testing.

| Property | Value | Why |
|---|---|---|
| Length | **6 digits** | Universal muscle memory; 1 in a million per guess |
| Generated by | **`randomInt` from `node:crypto`** | `Math.random()` is predictable and must never generate a secret |
| Stored as | **bcryptjs hash**, never plain text | A stolen database dump must not contain live codes |
| Lifetime | **5 minutes** (`OTP_TTL_MINUTES = 5`) | Long enough for slow mail, short enough that a leaked code is stale |
| Wrong guesses allowed | **5** (`OTP_MAX_ATTEMPTS = 5`) | 5 of a million is not a brute force |
| Single use | `consumed_at` stamped on success | A code in a mail thread cannot be replayed |
| Live codes per phone+purpose | **exactly one** | `createOtp()` retires older codes. Requesting a new one silently kills the old one |
| Yearly quota | **30 per phone per rolling 365 days** (`OTP_MAX_PER_YEAR = 30`) | Caps the worst-case bill and the abuse ceiling |
| Resend cooldown | **45 s server** (`OTP_COOLDOWN_SECONDS`), **60 s shown** | Stops one impatient user burning a third of their yearly allowance in a minute |
| Purposes | `'reset'` and `'first_login'` | Schema allows both; **only `'reset'` is ever written** today |
| Default channel | **email, for every account and every role** | Free, instant, no regulator |
| Channel switch | Always visible on screen | A parent with no email must be able to choose SMS |

Rolling-year means literally that — there is no monthly or daily bucket, and no
reset date. The query is:



SELECT count(*)::int AS used FROM otp_codes
WHERE phone_number = $1 AND created_at > now() - interval '365 days';


The rows in `otp_codes` **are** the history. That is why nothing is ever deleted
in normal operation, and why no extra counter table exists.

# PART 3 — The lifecycle, step by step

**Step 1 — `POST /api/auth/otp/send`**
Shape check on the phone number → generate 6 digits → hash them → insert one row
into `otp_codes` (which retires any earlier live code) → hand the plain code to
`sendMail()` or `sendSms()`.

**Step 2 — the user reads the code** from their inbox, or from the dev terminal
banner while `MAIL_PROVIDER=console`.

**Step 3 — `POST /api/auth/otp/verify`**
Finds the newest unconsumed, unexpired row for that phone and purpose → compares
the hash → on success stamps `consumed_at` **before** doing anything else, then
mints a **reset ticket**: a `jose` JWT with `purpose: 'reset'`, valid 10 minutes,
set as an httpOnly cookie named `reset`.

**Step 4 — `POST /api/auth/reset-password`**
Trusts **only** that cookie — never a phone number in the request body. Validates
the new password, writes the hash, bumps `session_epoch`, clears both cookies.
The user signs in fresh.

**Why the ticket exists:** without it, anyone who knew a phone number could call
the reset endpoint directly. The cookie proves *this browser* completed a
verification within the last 10 minutes, and there is no extra database table to
maintain because the JWT carries its own expiry.

**Why `consumeOtp` runs before the ticket is minted:** if minting failed after the
code was accepted but before it was retired, the same code would still be live.
Burn the code first, always.

# PART 4 — The quota, and what a user sees at the limit

At 31 requests in a rolling year, `otp/send` logs `[otp/send] BLOCKED: <phone>`
to the server and returns **the same 200 response as a successful send**. Nothing
is written, nothing is delivered.

That looks unhelpful, and it is deliberate: any response that differs — a
different message, a different status code, even a noticeably different response
time — tells a stranger whether a phone number is registered with the school.

**The consequence for you as the operator:** the browser can never tell you why
nothing arrived. The dev terminal always can. Judge OTP behaviour from the
terminal and the database, never from the screen.

**Runbook — "a parent says the code never arrives":**


- 1. Do they exist, and do they have an email?
SELECT id, role, full_name, email FROM profiles WHERE phone_number = '9810000001';
-- 2. How much of the yearly allowance is left?
SELECT count(*) FROM otp_codes
WHERE phone_number = '9810000001' AND created_at > now() - interval '365 days';
-- 3. What happened recently?
SELECT id, purpose, attempts, consumed_at IS NOT NULL AS used,
expires_at > now() AS still_valid, created_at
FROM otp_codes WHERE phone_number = '9810000001'
ORDER BY id DESC LIMIT 10;

If they are genuinely out of allowance and the request is legitimate, delete their
old rows — this is the intended manual override:

​
DELETE FROM otp_codes WHERE phone_number = '9810000001';


Raising `OTP_MAX_PER_YEAR` for everyone is the wrong fix for one person.

# PART 5 — The resend cooldown

**The attack it prevents is called SMS pumping.** An attacker (or a bored user)
hammers the "send code" button. Each press costs the school real money once SMS is
live, and every press consumes part of that number's yearly allowance.

Two layers, deliberately mismatched:

| Layer | Value | Behaviour |
|---|---|---|
| Server, `otpCooldownRemaining()` | **45 s** | Refuses silently, returns the identical generic 200, writes no row, consumes no quota, leaves the previous code valid |
| Browser, `CLIENT_COOLDOWN_SECONDS` | **60 s** | Disables the button and shows a live `Wait 0:43` countdown |

The browser number is **longer on purpose**, so a user who waits for the visible
countdown never meets an invisible refusal.

Three design details worth keeping:

1. **The elapsed time is computed in SQL**, from `created_at`, so the database
   clock is the only clock that counts. A user changing their computer's time
   changes nothing.
2. **The deadline is stored in `localStorage` as an absolute timestamp**, not as a
   countdown in React state. Before that fix, pressing F5 re-enabled the button
   while the server still silently refused — a confusing dead end. This and the
   theme setting are the only two things allowed in `localStorage`. Never a token.
3. **A refusal is measurably cheap and outwardly identical**: 22–46 ms versus
   163–584 ms for a real send. Same status, same body, same headers.

*Possible future upgrade, not built:* escalating backoff — 30 s, then 60 s, then
5 minutes. Only worth doing if abuse actually appears in the logs.

# PART 6 — Email

## 6.1 What is wired up

`lib/mailer.js` is the only file in the project that touches `nodemailer`. It
exports `sendMail({to, subject, text, html})` → `{delivered, provider, messageId}`.

Three modes, chosen by `MAIL_PROVIDER`:

| Mode | Behaviour |
|---|---|
| `console` | Prints a banner to the dev terminal, sends nothing. Costs ₹0, needs no account. Every OTP test in Feature 13 ran this way. |
| `gmail` | Real delivery through a Gmail App Password. **Currently in use and verified.** |
| `smtp` | Real delivery through any SMTP host. **The production path.** |

Two behaviours that matter to callers:

- **It throws only for programmer error** — a missing `to`, `subject` or `text`.
- **A delivery or configuration failure never throws.** It logs `[mailer] delivery
  failed` and returns `delivered: false`. A dead mail server must never become a
  500 on a parent's phone, and the route must never tell the browser whether
  delivery worked — "that address bounced" is the same account-enumeration leak we
  closed on the login route.

The transport is cached on `globalThis.__schoolAppMailer` for the same reason
`lib/db.js` caches its pool: Next.js reloads modules on every file save, and
without the guard you would leak a connection pool per keystroke.

It also strips spaces from `MAIL_PASS`, because Google displays App Passwords as
`abcd efgh ijkl mnop` and then rejects them with the spaces included.

## 6.2 Gmail App Password — the setup, for the record

Gmail refuses a plain account password from an app. You need a 16-character App
Password, and that option only appears once 2-Step Verification is on.

1. Sign in to the sending Google account.
2. **Google Account → Security → 2-Step Verification → turn it ON** (phone
   verification). This is mandatory; App Passwords do not exist without it.
3. Back in **Security**, search the page for **App passwords**.
4. Create one, name it `school-app`, and copy the 16 characters.
5. Put it in `.env.local` as `MAIL_PASS`. Spaces are stripped for you.
6. **Restart `npm run dev`** — environment variables are read once at boot.

Google shows the password exactly once. Lost it? Delete that entry and make a new
one.

## 6.3 Why Gmail is not the production answer

| Limit | Free Gmail | Workspace |
|---|---|---|
| Recipients per day | ~500 | ~2,000 |

Beyond that: Gmail rewrites the visible sender to the Gmail address, so parents see
a personal-looking address rather than the school; there is no delivery dashboard;
and one account being suspended silently stops all password resets. Fine for
development and a pilot. Not fine for 400 families.

## 6.4 Production email options

All of these work with **`MAIL_PROVIDER=smtp` and no code change** — that is the
entire point of the provider switch.

| Option | Free tier | Verdict |
|---|---|---|
| **Amazon SES** | ~$0.10 per 1,000 after a small free allowance | Cheapest at scale. Needs domain verification and a "leave sandbox" request. Best long-term choice. |
| **Brevo** | ~300 emails/day free | Easiest start, plain SMTP credentials. |
| **Resend** | ~3,000/month free | Very developer-friendly. |
| **Self-hosted Postfix on our VPS** | ₹0 | **Rejected.** Deliverability is the problem, not software. Fresh VPS IPs have no reputation, many hosts block port 25, and your reset emails land in spam. Running a mail server well is a full-time job. |

Rejecting Postfix is not a violation of the open-source rule — `nodemailer` is
MIT-licensed and we own the code. What we buy from SES or Brevo is IP reputation,
which cannot be self-hosted into existence.

**Three DNS records you will need on a real domain**, in plain English:

- **SPF** — a public list of who is allowed to send mail claiming to be your domain.
- **DKIM** — a cryptographic signature proving a message really came from you and
  was not altered in transit.
- **DMARC** — the policy telling receiving servers what to do when SPF or DKIM
  fails, and where to send reports.

Without all three, a good chunk of your mail goes to spam. Your provider generates
the exact values; you paste them into your domain's DNS.

## 6.5 Switching to production email

Add these to `.env.local` (the `smtp` branch already reads them):


MAIL_PROVIDER=smtp
MAIL_HOST=<from your provider>
MAIL_PORT=587
MAIL_SECURE=false        # true only for port 465
MAIL_USER=<from your provider>
MAIL_PASS=<from your provider>
MAIL_FROM=Greenwood School <no-reply@yourdomain.com>


Restart the server, then trigger one real reset and confirm the code arrives.
**No JavaScript changes.**

# PART 7 — SMS in India: the honest picture

## 7.1 There is no free SMS, and there is a legal step first

`lib/sms.js` has a `msg91` branch that is **intentionally not implemented**. It
logs an error and returns `delivered: false`. That is deliberate: wiring a
provider before registration is complete produces *silent* non-delivery, which is
far worse to debug than a loud refusal.

Every commercial SMS sent to an Indian number must come from a sender registered
on a **TRAI DLT platform** (Distributed Ledger Technology, mandated by the
telecom regulator to stop spam). Unregistered messages are simply not delivered —
no bounce, no error.

## 7.2 TRAI DLT registration, step by step

Budget **roughly ₹5,000 one-time** and **3–10 working days**.

1. **Pick one DLT portal.** Jio, Airtel, Vodafone Idea, BSNL and others each run
   one. Registering on any one is honoured across all operators, so choose the one
   with the friendliest interface.
2. **Register as a Principal Entity.** You will need the school's PAN, GST or
   registration certificate, an authorised person's ID and address proof, and a
   letter of authorisation on letterhead. Pay the fee.
3. **Receive your Entity ID** — a long numeric string. Keep it.
4. **Register a Header (Sender ID).** Six alphanumeric characters, e.g. `GRNWDS`.
   Choose the **Service-Implicit** category, not Promotional.
5. **Register the message template.** The text must be exact, with `{#var#}` where
   the code goes:
{#var#} is your Greenwood School verification code. It is valid for 5 minutes.
Do not share it with anyone.


6. **Wait for approval** (usually 1–3 days) and collect the **Template ID**.
7. **Open an account with an SMS gateway** and enter your Entity ID, Header and
   Template IDs there.
8. **Recharge and send one test message** to your own phone.

**Two rules that catch everyone:**

- **The message your code sends must match the approved template character for
  character**, apart from the variable. One extra full stop and the message is
  rejected.
- **Category matters.** Promotional messages are blocked for numbers registered on
  DND. Service-Implicit OTPs are delivered even to DND numbers — which is exactly
  why a password reset must be registered under that category and never as
  marketing. Register it wrongly and half your parents never receive a code.

## 7.3 Gateway comparison

Prices move; confirm at the time you buy. Indicative rates for Indian domestic SMS:

| Gateway | Approx. per SMS | DLT handling | Notes |
|---|---|---|---|
| **MSG91** | ₹0.15–0.20 | Entity/Template IDs are first-class API fields | India-focused, good documentation. Our stub is named for it. |
| **Fast2SMS** | ₹0.15–0.25 | Simple panel | Cheapest to start, thinner API and support. |
| **Gupshup / Kaleyra / Textlocal** | ₹0.15–0.25 | Similar to MSG91 | Reasonable alternatives. |
| **Twilio** | ₹0.55+ | You still must do DLT yourself | Global brand, roughly 3× the price for Indian traffic. Not worth it here. |

None of them removes the DLT requirement. A gateway that claims otherwise is
routing through someone else's registration, and that traffic gets cut off.

## 7.4 What the code needs when DLT is finished

The three environment keys already exist and are already empty placeholders:
SMS_PROVIDER=msg91
SMS_API_KEY=<from the gateway>
SMS_SENDER_ID=GRNWDS          # your approved 6-character header
SMS_DLT_TEMPLATE_ID=<from the DLT portal>

Then replace the `msg91` branch in `lib/sms.js` — and **only** that branch — with a
real HTTP call. Shape, not paste-ready code; check the gateway's current API docs
when you implement it:

​
if (PROVIDER === "msg91") {
try {
const res = await fetch("https://<gateway endpoint>", {
method: "POST",
headers: { "Content-Type": "application/json", authkey: process.env.SMS_API_KEY },
body: JSON.stringify({
sender: process.env.SMS_SENDER_ID,
template_id: process.env.SMS_DLT_TEMPLATE_ID,
mobiles: 91${to},          // country code, no plus sign
VAR1: <the code>,            // must match the {#var#} slots exactly
}),
});
if (!res.ok) { console.error("[sms] gateway rejected", res.status); return { delivered: false, provider: PROVIDER }; }
return { delivered: true, provider: PROVIDER };
} catch (err) {
console.error("[sms] delivery failed", err);
return { delivered: false, provider: PROVIDER };
}
}

**Four rules for whoever writes that code:**

1. **Never throw.** Return `{ delivered: false }` exactly as the console branch and
   `sendMail` do. Every caller depends on that.
2. **Never change `sendSms`'s signature.** `{ to, message }` in, `{ delivered,
   provider }` out. Callers must stay ignorant of the gateway.
3. **Never log the code itself** outside the console-provider banner.
4. **Do not touch `app/api/auth/otp/send/route.js`.** If the contract holds, the
   route needs no edit at all — that is the whole point of the split.

Keep `SMS_PROVIDER=console` until a real message has landed on a real phone.

# PART 8 — Choosing a channel

**Email is the default for every account and every role, and the switch to SMS is
always visible.** That was a deliberate reversal of the original plan, which was
SMS-first.

| Situation | What happens |
|---|---|
| Account has an email | Code goes to the inbox. Free. |
| Account has no email (all 400 seed parents today) | The user taps the switch and the code goes to the SMS path — the terminal banner today, a real message once DLT is done. |
| Account has neither, or the phone is not registered | The response is the same generic 200 and nothing is sent. Silence is the anti-enumeration rule working. |

The response body **always echoes the channel the user requested**, not the channel
actually used. Reporting "we fell back to SMS because you have no email on file"
would reveal whether an account exists and whether it has an email address.

**Operational note:** the seed staff addresses are `@greenwood.test`, a domain that
does not exist, so those mails silently fail. Real addresses must be collected
before go-live. Until then, only accounts pointed at a real inbox can receive a
code by email.

​
-- how many accounts can actually receive email today?
SELECT role, count(*) AS total, count(email) AS with_email
FROM profiles GROUP BY role ORDER BY role;

# PART 9 — Production go-live checklist for auth

Tick every line before real parents touch this.

**Email**
- [ ] A real domain, with SPF, DKIM and DMARC records published
- [ ] `MAIL_PROVIDER=smtp` with production credentials
- [ ] Real email addresses collected for parents and staff
- [ ] One live end-to-end reset tested from a phone on mobile data

**SMS**
- [ ] TRAI DLT entity registered, header approved, template approved
- [ ] Gateway account funded
- [ ] The `msg91` branch implemented and tested to a real handset
- [ ] `SMS_PROVIDER` switched off `console`

**Secrets and sessions**
- [ ] A fresh 64-character `JWT_SECRET` generated on the server, different from the
      development one. **Changing it signs out every user immediately** — it
      invalidates every existing token. Do it once, at deploy, not casually.
- [ ] `.env.local` never committed (already enforced by `.gitignore`)
- [ ] HTTPS in front of the app, so session cookies get the `secure` flag
      automatically

**Data**
- [ ] Every test account's password changed from `Pass@123`
- [ ] Automated PostgreSQL backups running and a restore actually tested
- [ ] `db/migrations/002_auth_columns.sql` applied to the production database

**Watch after launch**
- [ ] `audit_logs` reviewed for `auth.lockout` spikes (a spike is either an attack
      or a confusing login screen — both matter)
- [ ] The 4 outstanding npm advisories reviewed. **Never `npm audit fix --force`**;
      it would upgrade Next.js and break the build.
- [ ] Add CAPTCHA or per-IP throttling only if abuse actually appears in the logs

# PART 10 — Operational runbooks

Set these up once per PowerShell session:

cd C:projectsschool-app
$env:PGPASSWORD = "<db password>"
$psql = "C:Program FilesPostgreSQL16binpsql.exe"

**A locked-out user** (5 failed attempts, 15-minute lock, HTTP 423):

​
UPDATE profiles SET failed_login_attempts = 0, locked_until = NULL
WHERE phone_number = '9000000102';

**Sign one person out of every device** — stolen phone, staff departure:

​
UPDATE profiles SET session_epoch = session_epoch + 1
WHERE phone_number = '9000000001';

**Sign out absolutely everyone** — suspected key leak:

​
UPDATE profiles SET session_epoch = session_epoch + 1;
(Rotating `JWT_SECRET` does the same thing and additionally invalidates the
signature; use that if the secret itself leaked.)

**Force a password change at next sign-in:**

​
UPDATE profiles SET must_change_password = true WHERE phone_number = '9000000001';

**Inspect recent OTP activity:**

​
SELECT id, phone_number, purpose, attempts,
consumed_at IS NOT NULL AS used,
expires_at > now() AS still_valid, created_at
FROM otp_codes ORDER BY id DESC LIMIT 10;

**Clear one number's OTP history** (frees the yearly allowance):

​
DELETE FROM otp_codes WHERE phone_number = '9000000001';

**Testing warning:** every test send consumes the real 30-per-year allowance for
that number. The Feature 13 test rows were deleted afterwards for exactly this
reason. Test with one dedicated number, then clear it.

# PART 11 — What this costs

| Item | Cost |
|---|---|
| Development today (`console` + Gmail) | **₹0** |
| Email in production (SES) | ~₹9 per 1,000 messages |
| Email in production (Brevo free tier) | ₹0 up to ~300/day |
| TRAI DLT registration | **~₹5,000 one-time** |
| SMS gateway minimum recharge | typically ₹1,000+ prepaid |
| Per SMS | ₹0.15–0.25 |

**Realistic annual SMS bill.** 400 parents, assume two forgotten passwords each per
year, all by SMS: 800 × ₹0.20 = **₹160**. The absolute ceiling, if every account
exhausted its 30-per-year quota, is 400 × 30 × ₹0.20 = **₹2,400**. The quota exists
precisely so that number has a ceiling at all.

**The comparison that decided the design:** OTP as the *login* method, at roughly
423 accounts signing in on ~200 school days, lands near **₹25,000 a year** — before
a single password reset. Password-first plus email OTP costs effectively nothing.

# PART 12 — Invariants — do not break these in a later feature

1. **Never import `nodemailer` outside `lib/mailer.js`.** Call `sendMail()`.
2. **Never send SMS outside `lib/sms.js`.** Call `sendSms()`.
3. **Neither function may throw on a delivery failure.** Return `delivered: false`.
4. **Never tell the browser whether delivery succeeded**, and never vary the
   message, status code or timing based on whether an account exists.
5. **Never store or log a plain OTP** except in the console-provider banner.
6. **Never add a second rate-limit table.** The rows in `otp_codes` are the history.
7. **Never compute the cooldown from a browser clock.** The SQL does it.
8. **Never put a token in `localStorage`.** Only the theme and the cooldown
   deadline live there.
9. **Never move the `session_epoch` check into `proxy.js`.** The Edge runtime
   cannot load `pg`; the check belongs in Node pages and routes.
10. **Never lower the client cooldown below the server's 45 seconds** — users would
    hit an invisible refusal.
11. **Never widen `otp_codes.purpose`** beyond `'reset'` and `'first_login'` without
    a migration and a decision-log entry.
12. **Never invent a new audit action** for OTP or password events. There is none
    today, and that was deliberate — an audit row per reset would be noise.
